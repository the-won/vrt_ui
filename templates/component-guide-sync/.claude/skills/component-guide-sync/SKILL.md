# 컴포넌트 가이드 동기화

## 이 스킬이 하는 일

`resources/`(저장소 루트, 운영 중인 컴포넌트 소스 — 스타일시트·스크립트·마크업 템플릿 등)가 바뀌었을 때, `guide/`(저장소 루트, 컴포넌트 가이드 페이지)에 있는
해당 컴포넌트의 예시 마크업을 실제 변경 내용에 맞게 직접 고친다. 사람이 가이드 페이지를 별도로 관리하지 않아도
"운영 리소스 ↔ 가이드 페이지"가 어긋나지 않게 하는 것이 목적이다.

이 스킬은 보통 `guide-sync-server.js`가 `git diff`로 변경 파일 목록을 감지한 뒤,
`claude -p` 헤드리스 실행으로 이 스킬을 호출하면서 그 목록을 함께 전달하는 방식으로 실행된다.
(사람이 대화형으로 `/component-guide-sync`를 직접 불러도 동일하게 동작해야 한다.)

## 감지 대상 파일

저장소 루트의 `resources/` 폴더 전체. 여기엔 최소 두 종류의 서로 다른 소스가 섞여 있을 수 있다:

- **스타일/스크립트** (예: `resources/css/tokens.css`, `resources/css/components.css`,
  `resources/js/components/*.js`) — 클래스·모디파이어·상태의 존재 여부를 알려주는 소스.
- **마크업 템플릿** (예: `resources/templates/button.html`, `resources/templates/form.html`) —
  해당 컴포넌트를 실제로 사용할 때의 **정답 DOM 구조 그 자체**. 클래스명만 보고 구조를
  추측하지 말고, 이 템플릿이 있으면 반드시 이 템플릿을 source of truth로 삼는다.

guide-sync-server가 변경 파일 목록을 함께 전달하니, 그 목록으로 어떤 파일이 실제로 바뀌었는지,
그리고 그중 마크업 템플릿이 포함되어 있는지부터 확인한다.

## 작업 규칙 (반드시 지킬 것)

1. **새 스타일을 임의로 창작하지 않는다.** 변경된 리소스에 실제로 존재하는 클래스·모디파이어·상태만 예시로 추가한다.
2. **마크업 템플릿이 바뀌었다면 그게 최우선 근거다.** `resources/templates/*.html` 같은 마크업 템플릿이 변경 목록에
   있으면, CSS 클래스명에서 구조를 추측하지 말고 그 템플릿 파일을 Read해서 실제 마크업(태그 구조, 속성, 자식 순서)을
   그대로 가져와 가이드 예시에 반영한다. CSS만 바뀌고 마크업 템플릿은 안 바뀐 경우에만 클래스명 기반으로 판단한다.
3. **기존 예시 마크업의 컨벤션을 그대로 따른다.** 들여쓰기, 클래스 네이밍, 주석 스타일, 라벨 표기 방식 모두 인접한 기존 예시를 그대로 모방한다. 새로운 레이아웃 패턴을 발명하지 않는다(단, 마크업 템플릿 자체의 구조는 규칙 2에 따라 그대로 따름).
4. **매핑 우선순위**: (a) 기존 컴포넌트의 새 모디파이어/상태 추가 → 해당 섹션의 맞는 그룹(사이즈/스타일/정렬 등)에 예시 한 줄 추가. (b) 완전히 새로운 컴포넌트 종류 추가 → 기존 섹션 중 하나를 그대로 복제해 구조를 맞추고 내용만 교체. (c) 어느 쪽인지 애매하면 추측해서 만들지 말고, 무엇이 애매한지 요약에 남기고 건너뛴다.
5. **삭제된 클래스**는 가이드 페이지에서도 해당 예시를 제거한다(단, 확신이 없으면 지우지 말고 요약에 남긴다).
6. **커밋·푸시하지 않는다.** 파일 편집까지만 하고 git 명령은 절대 실행하지 않는다. 실제 반영 여부는 사람이 diff를 검토한 뒤 직접 커밋한다.
7. **가이드 페이지 외의 파일은 건드리지 않는다.** 운영 리소스(`resources/`)는 읽기만 하고 수정하지 않는다.

## 작업 순서

1. 전달받은 변경 파일 목록을 바탕으로 `git diff <이전 기준점> HEAD -- resources`를 읽어 실제로 무엇이 추가/변경/삭제됐는지 파악한다. 변경 목록에 `resources/templates/*.html` 같은 마크업 템플릿이 있으면 그 파일을 Read해서 실제 마크업 구조를 먼저 파악한다.
2. `guide/` 폴더를 읽어 현재 구조와 기존 예시 컨벤션을 파악한다.
3. 위 "매핑 우선순위" 규칙에 따라 가이드 페이지를 Edit 도구로 직접 수정한다(마크업 템플릿이 있는 컴포넌트는 규칙 2에 따라 템플릿 구조를 그대로 반영).
4. 마지막에 아래 형식으로 변경 요약을 출력한다(트리거 서버가 이 출력을 그대로 사용자에게 보여준다):

```
## 가이드 동기화 요약
- 추가: <컴포넌트/변형 이름> (<이유 — 어떤 리소스 변경(스타일/마크업 템플릿 등)에서 비롯됐는지>)
- 수정: ...
- 삭제: ...
- 건너뜀(애매함): ...
```

변경이 전혀 필요 없다고 판단되면(예: 감지된 변경이 가이드에 영향 없는 내부 리팩터링) 그 이유를 요약에 명시하고 파일은 건드리지 않는다.
